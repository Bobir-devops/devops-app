03 — Docker

Applicationni qutiga solish

Container — application uchun izolyatsiyalangan ish stoli.

Asosiy saroy: QUTIXONA. Retseptdan tayyor qutigacha bitta yo'nalishda yurasiz — Dockerfile → Image → Container → Application.

Qutixona bo'ylab sayohat
Bo'limlar
Bo'lim 1

Containerization nima?

Applicationni serverga shunchaki "Mana kod, ishlat" deb tashlash o'rniga uning runtime, dependencies, libraries, configuration, filesystem muhitini standartlashtirib, container ichida ishga tushiramiz.

Mental model:

Container — application uchun izolyatsiyalangan ish stoli.
🧠 Eslab qolish — Qutiga hammasi birga tushadi

"Menda ishlayapti, serverda ishlamayapti" muammosining ildizi — muhit farqi. Container o'sha muhitni kod bilan birga qadoqlaydi: runtime, kutubxonalar, sozlama, fayl tizimi.

Shuning uchun quti qayerga borsa — noutbukda, test serverda, productionda — ichi bir xil qoladi. Standart quti — butun Docker g'oyasining o'zagi.

🔤 Mnemonika — Konteyner izolyatsiyasi«Nimani ko'radi — Namespace, Chegarasi qancha — Cgroup». Namespace — ko'rinish (PID, NET, MNT), cgroup — resurs (CPU, xotira).

🧠 Eslab qolish — Alohida uy va alohida xona

VM — hovlida yangi uy qurish: o'z devori, o'z isitmasi, o'z OS'i. Ishonchli izolyatsiya, lekin og'ir va sekin.

Container — bitta binoda alohida xona: devor bor, lekin poydevor va isitish tizimi umumiy (host kerneli). Shuning uchun sekundlarda ochiladi va kam joy yeydi.

Bitta xulosa: izolyatsiya darajasi VM'da yuqoriroq, tezlik va zichlik containerda yuqoriroq.

Bo'lim 3 · 2-to'xtash

Image va Container

Image — retsept. Container — retsept asosida tayyorlangan ishlayotgan instance.

Image
  |
  +-- Container A
  |
  +-- Container B
  |
  +-- Container C

Bitta image'dan ko'p container yaratilishi mumkin.

🧠 Eslab qolish — Qolip va mahsulot

Image — o'zgarmas (immutable) qolip: bir marta build qilinadi, keyin tegilmaydi. Container — o'sha qolipdan chiqqan tirik nusxa: o'z process'i, o'z yozuv qatlami bor.

Shuning uchun "container'ni o'zgartirib qo'ydim" degan ish yo'qoladi — container o'chsa o'zgarish ham ketadi. O'zgarish kerak bo'lsa image qayta build qilinadi.

Bo'lim 4 · 1-to'xtash

Dockerfile

Dockerfile — image qanday build qilinishini tasvirlaydigan recipe.

FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

EXPOSE 8000

CMD ["python", "app.py"]

Bu yerda:

FROM      -> boshlang'ich image
WORKDIR   -> ishchi directory
COPY      -> fayllarni imagega olib kirish
RUN       -> build vaqtida command
EXPOSE    -> documentation/metadata
CMD       -> container start bo'lganda default command
🧠 Eslab qolish — Retseptdagi tartib tasodifiy emas

Yuqoridagi misolda COPY requirements.txt va RUN pip install kodni ko'chirishdan oldin turadi. Sababi cache: kod o'zgarganda ham dependency o'rnatish qayta bajarilmaydi.

Agar COPY . .ni yuqoriga chiqarsangiz — har kichik o'zgarishda hamma dependency qaytadan o'rnatiladi va build sekinlashadi.

EXPOSE hech qanday portni ochmaydi — bu faqat hujjat. Haqiqiy ochish -p bilan bo'ladi.

Bo'lim 5 · 4-to'xtash

RUN va CMD

Bu juda ko'p so'raladi.

RUN

Build vaqtida ishlaydi.

RUN apt-get update

Image yaratish jarayonining qismi.

CMD

Container ishga tushganda default command.

CMD ["python", "app.py"]

Mental model:

docker build
    |
    +-- RUN

docker run
    |
    +-- CMD
🧠 Eslab qolish — Ikki xil vaqt

RUN — quti yasalayotganda bajariladigan ish: paket o'rnatish, fayl tayyorlash. Natijasi image ichida muzlab qoladi.

CMD — quti ochilganda ishga tushadigan buyruq. Image ichida saqlanadi, lekin faqat docker run paytida bajariladi.

Adashmaslik uchun: RUN → build, CMD → run. Buyruq nomlari ham shundan.

Bo'lim 6 · 5-to'xtash

ENTRYPOINT va CMD

Eng yaxshi mental model:

ENTRYPOINT — asosiy executable.
CMD — default argumentlar.
ENTRYPOINT ["python"]
CMD ["app.py"]

Default: docker run image amalda python app.py. Agar docker run image test.py bersang, python test.py bo'lishi mumkin.

Shuning uchun ENTRYPOINT + CMD juftligini:

ENTRYPOINT = "nima ishga tushadi?"
CMD        = "defaultda nima argument beriladi?"

deb eslab qolish juda qulay.

🧠 Eslab qolish — Ijrochi almashmaydi, argument almashadi

ENTRYPOINT — o'zgarmas ijrochi. CMD — o'zgaruvchi argument. docker runga qo'shimcha so'z bersangiz, u CMD'ni almashtiradi, ENTRYPOINT joyida qoladi.

Shuning uchun CLI vositalarida odatda ENTRYPOINT — dasturning o'zi, CMD — eng ko'p kerak bo'ladigan argument. Foydalanuvchi faqat argumentni o'zgartiradi.

ENTRYPOINT'ni ham almashtirish kerak bo'lsa — --entrypoint flagi bilan.

🔤 Mnemonika — ENTRYPOINT va CMDENTRYPOINT — «Egasi» (o'zgarmas ijrochi, masalan python), CMD — «Cho'tka» (almashtiriladigan argument, masalan app.py). Ishga tushadi: ENTRYPOINT + CMD. Kubernetes'da: command = ENTRYPOINT, args = CMD — «Command Egarini, Args CMD'ni almashtiradi».

Bo'lim 7 · 3-to'xtash

Container lifecycle

created
   |
   v
running
   |
   v
exited

Containerning asosiy processi tugasa, container ham tugaydi. Masalan:

CMD ["echo", "hello"]

Container start bo'ladi: echo hello tugaydi. Shuning uchun:

Container "virtual server" emas.

Uning hayoti odatda asosiy process hayotiga bog'liq.

🧠 Eslab qolish — Quti process bilan yashaydi

Serverga o'xshab "yoqib qo'ydim, turadi" degan ish yo'q. Container ichidagi birinchi process (PID 1) tugasa — quti ham darhol yopiladi.

Shuning uchun "container darhol exit bo'lyapti" degan muammoning javobi deyarli har doim: CMD ishini tugatib qo'ydi yoki xato bilan chiqdi. docker ps -a exit code'ni, docker logs sababini ko'rsatadi.

Bir jumla: container — jarayon uchun quti, server emas.

🔤 Mnemonika — Exit kodlari0 — «hammasi joyida». 1 — «dastur o'zi yiqildi, logga qara». 137 — «o'ldirildi: OOM yoki kill», 143 — «muloyim to'xtatildi». Eslash: 128 + 9 = 137, 128 + 15 = 143.

Bo'lim 8 · troubleshooting

docker stop va docker kill

docker stop app

Graceful stopga harakat qiladi.

docker kill app

containerdagi asosiy processni majburan to'xtatish uchun signal yuboradi.

Linuxdagi SIGTERM/SIGKILL tushunchalari Dockerda ham juda muhim.

🧠 Eslab qolish — Avval so'ra, keyin majbur qil

docker stop — SIGTERM: "ishingni yig'ishtir va chiq". Dastur ulanishlarni yopadi, ma'lumotni saqlaydi. Belgilangan vaqt (default 10s) ichida chiqmasa Docker o'zi SIGKILL yuboradi.

docker kill — darhol SIGKILL: hech qanday yig'ishtirish yo'q. Ma'lumot yarim yozilgan qolishi mumkin — shuning uchun bu oxirgi chora.

Muhim amaliy nuqta: dastur SIGTERM'ni ushlashi kerak. Shell form CMD ishlatilsa PID 1 shell bo'lib qoladi va signal dasturga yetmaydi — exec form (CMD ["python","app.py"]) ishlatiladi.

Bo'lim 9

Docker networking

Container ichidagi localhost — containerning o'zi. Bu hostning localhosti emas.

Masalan container ichida 127.0.0.1:8080 degan application bo'lsa, u faqat shu container ichidan ko'rinishi mumkin. Agar host yoki boshqa container kirishi kerak bo'lsa, application qanday addressga bind qilinganini tekshirish kerak.

🧠 Eslab qolish — Har qutining o'z ichki eshigi bor

Networking bo'limidagi 127.0.0.1 qoidasi bu yerda ikki barobar muhim: container o'z tarmoq maydonida yashaydi, shuning uchun uning loopback'i host loopback'i bilan umuman bog'liq emas.

Xulosa: container ichida curl localhost:8080 ishlashi hech narsani isbotlamaydi — hostdan ishlashini tekshirish uchun bind address va port mapping kerak.

Bo'lim 10 · 6-to'xtash

0.0.0.0 Dockerda

Masalan Python application 127.0.0.1:8000 ga bind qilingan. Container ichidan curl localhost:8000 ishlaydi. Lekin hostdan published port orqali connection ishlamasligi mumkin.

Applicationni 0.0.0.0:8000 ga bind qilish ko'pincha container networking uchun kerak. Keyin docker run -p 8000:8000 image bilan port publish qilinadi.

Mental model:

Host:8000

Docker port mapping
   |
   v
Container:8000
   |

🧠 Eslab qolish — Zanjir oxirgi bo'g'inda uziladi

Port mapping to'g'ri bo'lsa ham, zanjirning oxirgi bo'g'ini — dasturning bind address'i — loopback'da turgan bo'lsa trafik yetib bormaydi.

Shuning uchun "container ichida ishlaydi, hostdan ishlamaydi" degan holatda birinchi qaraladigan narsa -p emas, dastur qaysi manzilga bind qilgani. Tekshirish: container ichida ss -lntup yoki dastur log'idagi "listening on ..." qatori.

Bo'lim 11

EXPOSE va -p

EXPOSE 8000

portni avtomatik internetga ochib qo'ymaydi. Bu image metadata/documentation.

Real publishing:

docker run -p 8000:8000 image

Mental model:

EXPOSE — "mening applicationim mana shu portdan foydalanadi."
-p — "hostdagi portni container portiga ulab qo'y."
🧠 Eslab qolish — Taxtacha eshikni ochmaydi

EXPOSE — devorga yozib qo'yilgan taxtacha: "bu yerda 8000-port ishlatiladi". Hujjat sifatida foydali, lekin hech kimni kiritmaydi.

-p — haqiqiy ulanish: hostdagi portga kelgan so'rovni container portiga o'giradi (ya'ni DNAT). Faqat shu flag trafikni kiritadi.

Shuning uchun "EXPOSE yozdim, lekin ochilmayapti" — normal holat. Ochilishi uchun -p kerak.

Bo'lim 12 · 7-to'xtash

Volume

Container filesystemi container lifecycle bilan bog'liq. Database ma'lumotlarini faqat container writable layerida saqlash xavfli.

Volume:

Container
   |
   v
Volume
   |
   v
Persistent data

Masalan PostgreSQL uchun persistent volume ishlatiladi.

🧠 Eslab qolish — Qutining ichi vaqtinchalik

Container ichiga yozilgan har narsa writable layerda turadi va quti o'chganda birga ketadi. Shuning uchun "restartdan keyin ma'lumot yo'qoldi" degan muammoning sababi deyarli har doim volume yo'qligi.

Volume — Docker boshqaradigan tashqi ombor: container o'chsa ham qoladi, boshqa containerga ulash mumkin. Bind mount — hostdagi aniq katalogni ichkariga ulash (development uchun qulay, lekin host yo'liga bog'lanadi).

Qoida: holat (state) container ichida turmaydi — DB, yuklangan fayl, sertifikat hammasi volume'da.

Bo'lim 13

Docker resources

Container CPU va memory bilan cheklanishi mumkin. Memory limitga urilganda container OOMKilled bo'lishi mumkin. Kuzatish:

docker stats

Bu yerda CPU, memory, network, block I/O kabi usage ko'rinadi.

🧠 Eslab qolish — Chegarani kim qo'ygan?

Container OOM — siz qo'ygan limitga urildi: host'da xotira bo'lsa ham container o'ldiriladi. Host OOM — mashinaning o'zida xotira tugadi va yadro qo'riqchisi eng "og'ir"ni tanlaydi.

Farqi amaliy: container OOM bo'lsa — limitni yoki dasturning xotira ishlatishini ko'rish kerak. Host OOM bo'lsa — mashinadagi hamma yukni ko'rish kerak.

docker stats — jonli oyna: CPU, xotira, tarmoq, disk I/O. "Kim yeyapti?" degan savolga birinchi javob shu yerdan keladi.

🔤 Mnemonika — CPU va xotira limiti«CPU sekinlatadi, xotira o'ldiradi». CPU oshsa — throttling, process tirik. Xotira oshsa — OOMKilled, exit 137.

Docker debugging

Container darhol chiqib ketdi:

docker ps -a

docker inspect

Container running, lekin app ishlamayapti:

1. logs
2. process
3. listening port
4. bind address
5. network
6. environment/config
7. dependencies

Containerlar bir-biriga ulanmayapti:

network
DNS
service/container name
port
application bind
firewall
🧠 Eslab qolish — Uch senariy, uch ro'yxat

Darhol chiqdi — savol "nega o'ldi?": docker ps -a exit code'ni, docker logs oxirgi gapini, docker inspect sozlamani ko'rsatadi.

Ishlayapti, javob yo'q — savol "qaysi bo'g'inda uzilgan?": log → process → port → bind address → network → config → dependency. Bu Networking bo'limidagi narvonning Docker varianti.

Bir-biriga ulanmayapti — tarmoq, DNS (container nomi), port, bind, firewall. Bitta tarmoqda emasligini yoki nomni noto'g'ri yozganini shu ketma-ketlik topadi.

Bo'lim 15

Docker Compose

Compose bir nechta service'ni birgalikda boshqarishga yordam beradi. Masalan:

frontend
backend
postgres
redis

barchasini bitta compose faylda tasvirlash mumkin.

services
networks
volumes

asosiy tushunchalar.

🧠 Eslab qolish — Uch kalit tushuncha

services — qaysi containerlar ishga tushadi. networks — qaysi tarmoqda va kim kim bilan gaplashadi. volumes — qaysi ma'lumot saqlanadi.

Compose bitta tarmoq yaratadi va service'lar bir-birini nom orqali topadi: backend postgres:5432 deb ulanadi — IP yozish kerak emas.

Muhim tuzoq: depends_on faqat start tartibini belgilaydi, service tayyorligini kafolatlamaydi. Tayyorlik uchun healthcheck yoki dasturda retry kerak.

Bo'lim 16 · troubleshooting

Dockerda "ignore"

Docker'da container uchun umumiy ignore degan lifecycle command yo'q.

"Container ishlamay qolsin, lekin e'tiborga olinmasin" kabi xatti-harakat kerak bo'lsa, asl muammoni aniqlash kerak: process exit, restart policy, healthcheck, logs, dependency, resource kabi tushunchalar bilan boshqariladi.

🧠 Eslab qolish — Yashirish emas — boshqarish

Docker'da "bu containerni hisobga olma" degan tugma yo'q, va bu ataylab shunday: container sog'lom yoki sog'lom emas — o'rtasi yo'q.

Kerakli xatti-harakatni aniq vositalar bilan aytasiz: restart policy ("o'lsa tiriltma" — --restart=no), healthcheck ("sog'lomligini shu bilan o'lcha"), dependency ("buni kutma").

Ya'ni savol "qanday e'tiborsiz qoldiraman?" emas, "nega o'lyapti?" — javob logda va exit code'da.

🧠 Eslab qolish — Bitta yo'nalish, to'rt o'lcham

Shuning uchun debug qilganda "Docker buzuq" degan xulosa deyarli hech qachon to'g'ri bo'lmaydi — to'rttadan qaysi biri ekanini aytish kerak.

Bo'lim 18 · 🧩 qo'shimcha

xavfsiz va kichik image

# syntax=docker/dockerfile:1
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                  # kesh: dependency alohida qatlam
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/api

FROM gcr.io/distroless/static:nonroot
COPY --from=build /app /app
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
  • Multi-stage — compiler yakuniy image‘ga tushmaydi.
  • Root emas (USER), readOnlyRootFilesystem, capability olib tashlash.
  • Asos image aniq teg yoki digest bilan; latest emas.
  • .dockerignore — .git, .env, node_modules.
  • Secret build‘ga --secret (BuildKit) bilan, ARG/ENV bilan emas — ular image tarixida qoladi (docker history).
  • HEALTHCHECK va exec form ENTRYPOINT.
⇄ Ko'priklar

Docker va Kubernetes — bir xil g'oyalar

Kubernetes Docker'ni almashtirmaydi — uning tushunchalarini ko'p mashinaga tarqatadi. Chap ustundagini bilsangiz, o'ng ustundagisi tanish ko'rinadi.

Image ⇄ Pod template
O'zgarmas qolip — ikkisida ham nusxalar shundan chiqadi.
Container ⇄ Pod ichidagi konteyner
Bir xil narsa — Kubernetes uni Pod ichiga o'raydi.
docker run -p ⇄ Service / NodePort
Tashqi portni ichki portga ulash — ikkisi ham NAT.
docker stop ⇄ SIGTERM + terminationGracePeriod
Avval muloyim so'rov, keyin majburan.
restart policy ⇄ restartPolicy + kubelet
"O'lsa tiriltmi?" degan bir xil savol.
healthcheck ⇄ liveness / readiness probe
Sog'lomlikni kim va qanday o'lchaydi.
Volume ⇄ PersistentVolumeClaim
Holat container tashqarisida saqlanadi.
docker-compose.yml ⇄ Deployment + Service + PVC
Bitta faylda butun stack — miqyosi boshqa, g'oya bir xil.
0.0.0.0 ga bind ⇄ Pod tashqaridan ko'rinmaydi
Loopback'ga bind qilinsa Service ham yordam bermaydi.
docker stats ⇄ kubectl top
Kim resurs yeyapti degan savol.

15 savol

Docker asoslari

1 Docker nima?
✓ 🧠 Javob

Applicationni container ichida qadoqlab, tarqatib va ishga tushiradigan platforma. Kod bilan birga runtime, kutubxona, sozlama va filesystem'ni standart qutiga soladi — shuning uchun quti qayerda ochilsa ham ichi bir xil qoladi.

2 Containerization nima?
✓ 🧠 Javob

Applicationning runtime, dependencies, libraries, configuration, filesystem muhitini standartlashtirib, izolyatsiyalangan container ichida ishga tushirish. "Mana kod, ishlat" o'rniga "mana to'liq muhit, ishlat".

3 Virtualization va containerization farqi?
✓ 🧠 Javob

Virtualization — hardware darajasida: hypervisor har VM uchun alohida guest OS ko'taradi. Containerization — OS darajasida: containerlar host kernelini baham ko'radi, faqat foydalanuvchi maydoni ajratiladi. Shu sababli container yengil va tez start qiladi.

4 Container va VM farqi?
✓ 🧠 Javob

VM zanjiri: Hardware → Hypervisor → VM → Guest OS → Application. Container zanjiri: Hardware → Host OS/Kernel → Container runtime → Container → Application. Container kernelni share qiladi, VM esa alohida kernelga ega — izolyatsiya VM'da kuchliroq, tezlik va zichlik containerda yuqoriroq.

5 Docker Engine nima?
✓ 🧠 Javob

Docker'ning ishlaydigan qismi: daemon (containerlarni boshqaradi), REST API va CLI. Ya'ni image build qilish, container yaratish, tarmoq va volume boshqarish shu Engine ustida bajariladi.

6 Docker daemon nima?
✓ 🧠 Javob

Fon rejimida ishlaydigan xizmat (dockerd): haqiqiy ishni u qiladi — image build qiladi, container yaratadi va kuzatadi, tarmoq va volume boshqaradi. CLI faqat unga buyruq yuboradi.

7 Docker CLI nima?
✓ 🧠 Javob

Terminaldagi docker buyrug'i — client. O'zi hech narsa yaratmaydi: so'rovni daemon'ga uzatadi va javobni ko'rsatadi.

8 Docker client va daemon qanday bog'lanadi?
✓ 🧠 Javob

REST API orqali — odatda mahalliy Unix socket /var/run/docker.sock ustidan, masofadan esa TCP orqali. Shuning uchun CLI boshqa mashinadagi daemon'ni ham boshqarishi mumkin (DOCKER_HOST).

9 Image nima?
✓ 🧠 Javob

Container yaratish uchun o'zgarmas qolip (retsept natijasi): fayl tizimi qatlamlari va metadata (CMD, ENTRYPOINT, ENV, EXPOSE). O'zi ishlamaydi — undan container ochiladi.

10 Container nima?
✓ 🧠 Javob

Image'dan yaratilgan ishlayotgan instance: o'z process'i, o'z tarmoq maydoni, o'z yozuv qatlami bor. Application uchun izolyatsiyalangan ish stoli.

11 Image va container farqi?
✓ 🧠 Javob

Image — retsept, o'zgarmas, diskda turadi. Container — retsept asosida tayyorlangan tirik nusxa. Bitta image'dan ko'p container yaratiladi va har biri alohida yashaydi.

12 Registry nima?
✓ 🧠 Javob

Image'lar saqlanadigan va tarqatiladigan ombor. docker push bilan yuboriladi, docker pull bilan olinadi. Ommaviy (Docker Hub) yoki xususiy (ECR, GCR, Harbor) bo'lishi mumkin.

13 Docker Hub nima?
✓ 🧠 Javob

Docker'ning ommaviy registry'si — rasmiy va jamoa image'lari shu yerda turadi. FROM python:3.12-slim yozganingizda image aynan shu yerdan olinadi (boshqa registry ko'rsatilmasa).

14 Layer nima?
✓ 🧠 Javob

Dockerfile'dagi har instruction natijasida hosil bo'ladigan fayl tizimi qatlami. Image — qatlamlar yig'indisi. Qatlamlar qayta ishlatiladi: bir xil qatlam bir marta saqlanadi va cache'da qoladi — shuning uchun build tez bo'ladi.

15 Image immutable deyilishi nimani anglatadi?
✓ 🧠 Javob

Image bir marta build qilingandan keyin o'zgarmaydi. Container ichida fayl o'zgartirsangiz, o'zgarish container'ning writable layerida qoladi — image'ga tegmaydi. O'zgarish kerak bo'lsa yangi image build qilinadi (yangi teg bilan).

Dockerfile

16 Dockerfile nima?
✓ 🧠 Javob

Image qanday build qilinishini tasvirlaydigan retsept — matnli fayl. Har qatori (instruction) bitta qadam: asos image, fayl ko'chirish, buyruq bajarish, start buyrug'i.

17 Dockerfile qanday ishlaydi?
✓ 🧠 Javob

docker build instruction'larni yuqoridan pastga bajaradi; har biri natijasini yangi layerga yozadi. Oxirida hamma qatlam va metadata birlashib image bo'ladi. O'zgarmagan qadamlar cache'dan olinadi.

18 FROM nima?
✓ 🧠 Javob

Boshlang'ich image — build shu asosdan boshlanadi. Masalan FROM python:3.12-slim. Birinchi instruction bo'lishi kerak (ARG'dan keyin bo'lishi mumkin) va multi-stage build'da bir nechta bo'lishi mumkin.

19 RUN nima?
✓ 🧠 Javob

Build vaqtida bajariladigan buyruq — natijasi image qatlamida muzlab qoladi. Masalan RUN pip install -r requirements.txt. Container ishga tushganda qayta bajarilmaydi.

20 COPY va ADD farqi?
✓ 🧠 Javob

COPY — faqat lokal fayl/katalogni image ichiga ko'chiradi; oddiy va oldindan aytib beriladigan. ADD — qo'shimcha "aqli" bor: URL'dan yuklashi va arxivni avtomatik ochishi mumkin. Shu sehr tufayli amaliyotda COPY tavsiya etiladi, ADD faqat arxiv ochish kerak bo'lganda.

21 WORKDIR nima?
✓ 🧠 Javob

Keyingi instruction'lar va container start'i uchun ishchi katalog. WORKDIR /app yozilsa, keyingi COPY, RUN, CMD shu katalogda bajariladi — cd yozib yurish kerak emas.

22 ENV nima?
✓ 🧠 Javob

Image'ga yoziladigan environment variable — build vaqtida ham, container ishlaganda ham mavjud bo'ladi. Sozlama uchun ishlatiladi. Muhim: ENV qiymati image ichida ko'rinadi — secret bu yerga yozilmaydi.

23 ARG nima?
✓ 🧠 Javob

Faqat build vaqtida mavjud bo'ladigan o'zgaruvchi (--build-arg bilan beriladi). Container ishga tushganda yo'q. Lekin build tarixida qolishi mumkin — secret uchun bu ham ishonchli emas.

24 EXPOSE nima?
✓ 🧠 Javob

Image metadata / hujjati: "bu application shu portdan foydalanadi". Hech qanday portni ochmaydi va publish qilmaydi. Haqiqiy ochish docker run -p bilan bo'ladi.

25 USER nima?
✓ 🧠 Javob

Keyingi instruction'lar va container process'i qaysi foydalanuvchi nomidan ishlashini belgilaydi. Default — root; USER app bilan root bo'lmagan foydalanuvchiga o'tiladi — bu xavfsizlik uchun muhim.

26 ENTRYPOINT nima?
✓ 🧠 Javob

Container ishga tushganda bajarilaladigan asosiy executable. docker runga berilgan qo'shimcha so'zlar uni almashtirmaydi — argument sifatida qo'shiladi. Almashtirish uchun --entrypoint kerak.

27 CMD nima?
✓ 🧠 Javob

Container start bo'lganda default command yoki ENTRYPOINT uchun default argument. docker run image berilsa, CMD almashtiriladi.

28 CMD va ENTRYPOINT farqi?
✓ 🧠 Javob

ENTRYPOINT — "nima ishga tushadi?" (o'zgarmas ijrochi). CMD — "defaultda qanday argument beriladi?" (o'zgaruvchi). Runtime argument CMD'ni almashtiradi, ENTRYPOINT joyida qoladi.

29 CMD ["python","app.py"] ga runtime argument bersangiz nima bo'ladi?
✓ 🧠 Javob

ENTRYPOINT yo'q bo'lsa, butun CMD almashtiriladi: docker run image ls -la desangiz python app.py umuman ishlamaydi — ls -la bajariladi. Shuning uchun ijrochini qat'iy qilish kerak bo'lsa ENTRYPOINT ishlatiladi.

30 ENTRYPOINT bilan CMD birga ishlatilsa nima bo'ladi?
✓ 🧠 Javob

Ular birlashadi: ENTRYPOINT ["python"] + CMD ["app.py"] → python app.py. Runtime'da docker run image test.py berilsa → python test.py. Ya'ni CMD default argument rolini o'ynaydi.

31 RUN va CMD farqi?
✓ 🧠 Javob

RUN — docker build vaqtida bajariladi, natijasi image ichida qoladi. CMD — docker run vaqtida bajariladi, image ichida faqat "buyruq" sifatida yoziladi. Ikki boshqa vaqt.

32 Dockerfile'dagi instructionlar qaysi tartibda bajariladi?
✓ 🧠 Javob

Yuqoridan pastga, yozilgan tartibda — har biri oldingisining natijasi ustiga qatlam qo'yadi. Shu sababli tartib build tezligiga ta'sir qiladi: kam o'zgaradigan qadamlar yuqorida turishi kerak.

33 Dockerfile cache qanday ishlaydi?
✓ 🧠 Javob

Har instruction uchun Docker oldingi build natijasini qayta ishlatishga harakat qiladi: instruction va uning kirishi (COPY qilinayotgan fayllar) o'zgarmagan bo'lsa — qatlam cache'dan olinadi. Bitta qadam o'zgarsa, undan keyingi hamma qadam qaytadan bajariladi.

34 Cache invalidation qachon bo'ladi?
✓ 🧠 Javob

Instruction matni o'zgarganda, COPY/ADD qilinayotgan fayl mazmuni o'zgarganda, --build-arg qiymati o'zgarganda yoki asos image yangilanganda. Shuning uchun COPY . .ni yuqoriga chiqarish — har o'zgarishda dependency'ni qaytadan o'rnatish degani.

35 Multi-stage build nima?
✓ 🧠 Javob

Bitta Dockerfile'da bir nechta FROM: birinchi bosqichda kod compile/build qilinadi, oxirgi bosqichga faqat natija ko'chiriladi (COPY --from=build). Natija: compiler, dev-kutubxonalar va build artefaktlari yakuniy image'ga tushmaydi — image kichik va xavfsiz bo'ladi.

36 Nega production image kichik bo'lishi kerak?
✓ 🧠 Javob

Uch sabab: tez tarqaladi (pull vaqti va registry trafigi kam), hujum yuzasi kichik (kerak bo'lmagan paket = kamroq zaiflik), tez start qiladi va diskni kam yeydi. Shuning uchun slim/alpine asoslar va multi-stage build ishlatiladi.

37 Dockerfile best practices qanday?
✓ 🧠 Javob

Kichik asos image; multi-stage build; kam o'zgaradigan qadamlarni yuqoriga qo'yib cache'dan foydalanish; .dockerignore yozish; exec form CMD/ENTRYPOINT (signal to'g'ri yetishi uchun); USER bilan root'dan chiqish; secret'ni image'ga yozmaslik; teglarni aniq qilish (latestga tayanmaslik); bitta container — bitta vazifa.

CMD / ENTRYPOINT senariylari

38 ENTRYPOINT ["python"], CMD ["app.py"] bo'lsa container nima ishga tushiradi?
✓ 🧠 Javob

Ikkisi birlashadi: python app.py. ENTRYPOINT — ijrochi, CMD — unga beriladigan default argument.

39 Shu containerga docker run image test.py bersangiz nima bo'ladi?
✓ 🧠 Javob

Runtime argument CMD'ni almashtiradi → python test.py. ENTRYPOINT (python) o'zgarmaydi.

40 Shell form va exec form farqi?
✓ 🧠 Javob

Exec form — CMD ["python","app.py"]: buyruq to'g'ridan bajariladi va PID 1 bo'ladi. Shell form — CMD python app.py: aslida /bin/sh -c "python app.py" ishga tushadi, ya'ni PID 1 — shell. Amaliyotda exec form tavsiya etiladi.

41 ENTRYPOINT'ni runtime'da qanday override qilasiz?
✓ 🧠 Javob

docker run --entrypoint /bin/sh image — ENTRYPOINT almashtiriladi. Debug uchun juda qulay: quti ichiga kirib nima borligini ko'rish mumkin.

42 CMD'ni runtime argument bilan qanday override qilasiz?
✓ 🧠 Javob

Shunchaki docker rundan keyin yozasiz: docker run image . ENTRYPOINT bo'lsa — argument sifatida qo'shiladi; ENTRYPOINT bo'lmasa — butun buyruq almashadi.

43 ENTRYPOINT "asosiy command", CMD "default argument" sifatida qanday tushuniladi?
✓ 🧠 Javob

CLI vosita yasayotgandek o'ylang: ENTRYPOINT — dasturning o'zi (foydalanuvchi o'zgartirmaydi), CMD — eng ko'p kerak bo'ladigan argument (foydalanuvchi bemalol almashtiradi). Shu juftlik image'ni "buyruq" kabi ishlatishga imkon beradi.

44 Nega shell form PID 1 bilan bog'liq muammo chiqarishi mumkin?
✓ 🧠 Javob

Shell form'da PID 1 — /bin/sh, dastur esa uning bolasi. docker stop yuborgan SIGTERM shell'ga tushadi va ko'p qobiqlar uni bolasiga uzatmaydi. Natijada dastur graceful yopilmaydi va timeout'dan keyin SIGKILL bilan uzib tashlanadi. Exec form bu muammoni yo'q qiladi.

12 savol

Container lifecycle

45 Container lifecycle qanday?
✓ 🧠 Javob

created → running → exited. Container yaratiladi, asosiy process ishga tushadi, process tugaganda container ham tugaydi. Oraliq holatlar: paused, restarting, dead.

46 Container nega darhol exit bo'ladi?
✓ 🧠 Javob

Chunki uning asosiy process'i tugadi. Masalan CMD ["echo","hello"] — chop etadi va chiqadi. Yoki dastur xato bilan yiqildi. Container "virtual server" emas — hayoti PID 1 hayotiga bog'liq. Sabab: docker ps -a (exit code) va docker logs.

47 docker run nima qiladi?
✓ 🧠 Javob

Ikki ishni birga: image'dan container yaratadi (create) va uni ishga tushiradi (start). Image lokalda bo'lmasa avval pull qiladi.

48 docker start va docker run farqi?
✓ 🧠 Javob

run — yangi container yaratib ishga tushiradi. start — mavjud, to'xtagan containerni qaytadan yuradi (o'sha yozuv qatlami bilan). Ya'ni run har safar yangi nusxa, start — eskisini davom ettirish.

49 docker stop nima qiladi?
✓ 🧠 Javob

Asosiy process'ga SIGTERM yuboradi — "ishingni yig'ishtir va chiq". Belgilangan muddat (default 10 sekund) ichida chiqmasa, Docker SIGKILL yuboradi. Ya'ni graceful to'xtatishga harakat.

50 docker kill nima qiladi?
✓ 🧠 Javob

Darhol SIGKILL yuboradi (yoki --signal bilan ko'rsatilgan signalni). Hech qanday yig'ishtirish yo'q — yarim yozilgan fayl qolishi mumkin. Oxirgi chora.

51 docker restart nima qiladi?
✓ 🧠 Javob

stop + start — containerni to'xtatib qaytadan yuradi. Yangi container yaratilmaydi, image ham qayta olinmaydi. Sozlama o'zgartirilgan bo'lsa, restart yetmaydi — yangi container kerak.

52 docker rm nima qiladi?
✓ 🧠 Javob

To'xtagan containerni o'chiradi — u bilan birga writable layer va unda saqlangan ma'lumot ham ketadi. Ishlayotgan containerni o'chirish uchun -f kerak. Image'ga tegmaydi (u docker rmi bilan o'chiriladi).

53 Restart policy nima?
✓ 🧠 Javob

Container o'lsa Docker qanday munosabatda bo'lishi: no (tiriltmaydi), on-failure (faqat xato bilan chiqsa), always (har holda, daemon start'ida ham), unless-stopped (qo'lda to'xtatilmagan bo'lsa). docker run --restart=... bilan beriladi.

54 Exit code nima?
✓ 🧠 Javob

Process chiqqanda qoldiradigan raqamli natija: 0 — muvaffaqiyat. 1 — umumiy xato. 137 — SIGKILL bilan o'ldirilgan (ko'pincha OOM). 143 — SIGTERM bilan to'xtagan. 126/127 — buyruq bajarilmadi / topilmadi. docker ps -a ustunida ko'rinadi.

55 OOMKilled nima?
✓ 🧠 Javob

Container xotira limitiga urilgani uchun yadro tomonidan o'ldirilgani. docker inspectda OOMKilled: true ko'rinadi, exit code 137 bo'ladi. Sabab: limit juda kichik yoki dastur xotirani ko'p yeyapti (leak).

56 Zombie process Docker'da qanday muammo tug'diradi?
✓ 🧠 Javob

Container ichida PID 1 bolalarini reap qilishi kerak. Oddiy dastur PID 1 bo'lsa buni qilmaydi — tugagan bolalar zombie bo'lib jadvalda yig'ilib qoladi va PID jadvalini to'ldirishi mumkin. Yechim: --init flagi yoki tini kabi init process ishlatish.

16 savol

Docker networking

57 Docker networking qanday ishlaydi?
✓ 🧠 Javob

Har container o'z tarmoq maydonida (network namespace) yashaydi: o'z interfeysi, o'z IP'si, o'z loopback'i. Docker ularni virtual bridge orqali bir-biriga va tashqariga ulaydi; tashqariga chiqish SNAT, ichkariga kirish -p bilan DNAT orqali bo'ladi.

58 Bridge network nima?
✓ 🧠 Javob

Default tarmoq turi: Docker host'da virtual ko'prik (docker0) yaratadi, containerlar shunga ulanadi va private IP oladi. Tashqariga NAT orqali chiqadi. Foydalanuvchi yaratgan bridge'da containerlar bir-birini nom orqali topadi.

59 Host network nima?
✓ 🧠 Javob

Container host'ning tarmoq maydonini to'g'ridan ishlatadi — alohida IP olmaydi, port mapping ham kerak emas (dastur to'g'ridan host portini egallaydi). Tez, lekin izolyatsiya yo'q va port to'qnashuvi bo'lishi mumkin.

60 None network nima?
✓ 🧠 Javob

Containerda faqat loopback qoladi — tashqi tarmoq yo'q. Tarmoq kerak bo'lmagan yoki tarmoqni o'zingiz qo'lda sozlaydigan holatlar uchun (maksimal izolyatsiya).

61 Overlay network nima?
✓ 🧠 Javob

Bir nechta host ustidan yoyilgan virtual tarmoq: turli mashinalardagi containerlar bitta tarmoqdagidek gaplashadi (trafik tunnel orqali ketadi). Swarm/klaster muhitlari uchun ishlatiladi.

62 Container ichidagi localhost nimani anglatadi?
✓ 🧠 Javob

Containerning o'zini — host'ni emas, boshqa containerni ham emas. Har container o'z loopback'iga ega. Shuning uchun container ichida curl localhost:8080 ishlashi tashqaridan ishlashini isbotlamaydi.

63 0.0.0.0 Docker'da nega muhim?
✓ 🧠 Javob

Dastur 127.0.0.1ga bind qilgan bo'lsa, faqat container ichidan kirish mumkin — port mapping bo'lsa ham hostdan yetib borilmaydi. 0.0.0.0ga bind qilinsa containerning hamma interfeysida eshitadi va -p orqali kelgan trafik yetib boradi.

64 Port mapping qanday ishlaydi?
✓ 🧠 Javob

docker run -p 8000:8000 image — hostdagi 8000-portga kelgan so'rov container'ning 8000-portiga DNAT bilan o'giriladi. Zanjir: Host:8000 → port mapping → Container:8000 → Application.

65 EXPOSE va -p farqi?
✓ 🧠 Javob

EXPOSE — image metadata/hujjati: "shu port ishlatiladi", hech narsa ochmaydi. -p — haqiqiy publish: host portini container portiga ulaydi. Faqat -p trafikni kiritadi.

66 Containerlar bir-biri bilan qanday gaplashadi?
✓ 🧠 Javob

Bir xil foydalanuvchi tarmog'ida bo'lsa — container/service nomi orqali: Docker ichki DNS nomni container IP'siga yechadi (postgres:5432). Default bridge'da bu ishlamaydi — shuning uchun o'z tarmog'ingizni yaratish yoki Compose ishlatish kerak.

67 Container DNS qanday ishlaydi?
✓ 🧠 Javob

Docker'ning ichki DNS server'i (127.0.0.11) container nomlarini IP'ga yechadi va tashqi nomlarni host resolveriga uzatadi. Shuning uchun IP yozib yurish kerak emas — container qayta yaratilib IP o'zgarsa ham nom ishlaydi.

68 Container IP o'zgarishi mumkinmi?
✓ 🧠 Javob

Ha — container qayta yaratilganda yoki Docker qayta ishga tushganda IP o'zgarishi mumkin. Shuning uchun konfiguratsiyada IP emas, nom ishlatiladi.

69 Docker network inspect nima ko'rsatadi?
✓ 🧠 Javob

Tarmoqning to'liq tavsifi: driver turi, subnet va gateway, qaysi containerlar unga ulangani va ularning IP'lari. "Ikki container bir tarmoqdami?" degan savolga eng to'g'ri javob shu yerdan keladi.

70 Container tarmoqqa ulanmayotganini qanday tekshirasiz?
✓ 🧠 Javob

Zanjir bilan: docker network inspect — bir tarmoqdami; nomni yechadimi (container ichida getent hosts yoki nslookup); port ochiqmi (nc -vz); dastur qaysi manzilga bind qilgan (ss -lntup); firewall to'smayaptimi. Ya'ni tarmoq → DNS → nom → port → bind → firewall.

71 docker exec bilan tarmoqni qanday debug qilasiz?
✓ 🧠 Javob

Container ichiga kirib xuddi oddiy serverdagidek tekshirasiz: docker exec -it app sh, keyin ss -lntup, getent hosts db, curl -I http://db:5432, ip addr. Muhim: ko'p slim image'da bu vositalar yo'q — shuning uchun curl/wget borligini tekshirish yoki debug container ulash kerak.

72 Docker'da NAT qanday ishlatiladi?
✓ 🧠 Javob

Ikki yo'nalishda: container tashqariga chiqqanda SNAT — manba manzil host IP'siga almashtiriladi; -p bilan ochilgan portga kelgan so'rovda DNAT — manzil container IP:port'iga o'giriladi. Ya'ni Docker port mapping — bu NAT qoidasi.

Volumes

73 Volume nima?
✓ 🧠 Javob

Docker boshqaradigan doimiy ombor — container tashqarisida yashaydi. Container o'chsa ham ma'lumot qoladi va boshqa containerga ulanishi mumkin.

74 Nega container filesystem persistent emas?
✓ 🧠 Javob

Container ichiga yozilgan hamma narsa writable layerda turadi va u container bilan bog'langan — container o'chsa, qatlam ham o'chadi. Shuning uchun "restartdan keyin ma'lumot yo'qoldi" muammosining sababi deyarli har doim volume yo'qligi.

75 Bind mount nima?
✓ 🧠 Javob

Host'dagi aniq katalogni container ichiga ulash: -v /home/user/app:/app. Development uchun qulay (kod o'zgarishi darhol ko'rinadi), lekin host yo'liga bog'lanadi va ko'chirish qiyin.

76 Volume va bind mount farqi?
✓ 🧠 Javob

Volume — Docker o'zi boshqaradigan joyda saqlanadi, nomi bor, ko'chirish va backup qilish oson, production uchun mos. Bind mount — host'dagi aniq yo'l, host tuzilishiga bog'liq, development uchun qulay.

77 tmpfs mount nima?
✓ 🧠 Javob

Faqat xotirada yashaydigan ulanish — diskka yozilmaydi va container to'xtaganda yo'qoladi. Vaqtinchalik fayl yoki maxfiy ma'lumotni diskda qoldirmaslik kerak bo'lganda ishlatiladi.

78 Volume qanday yaratiladi va ulanadi?
✓ 🧠 Javob

docker volume create data bilan yaratiladi, docker run -v data:/var/lib/postgresql/data image bilan ulanadi (yoki --mount sintaksisi bilan). Compose'da volumes: bo'limida e'lon qilinadi.

79 Database'ni Docker'da ishlatishda nimaga e'tibor berish kerak?
✓ 🧠 Javob

Ma'lumot albatta volume'da bo'lishi; versiya yangilanganda ma'lumot formati mosligi; backup strategiyasi (volume'dan dump olish); resurs limitlari; bitta ma'lumot katalogiga bir vaqtda bitta DB container yozishi; graceful stop (ma'lumot buzilmasligi uchun SIGTERM'ni ushlash).

80 Volume o'chirilsa nima bo'ladi?
✓ 🧠 Javob

Undagi ma'lumot butunlay ketadi — tiklash faqat backup'dan mumkin. docker volume rm ishlatilayotgan volume'ni o'chirmaydi, lekin docker volume prune ishlatilmayotgan hamma volume'ni o'chirib tashlashi mumkin — shuning uchun ehtiyot bo'lish kerak.

81 docker volume ls nima ko'rsatadi?
✓ 🧠 Javob

Host'dagi mavjud volume'lar ro'yxatini (driver va nom bilan). docker volume inspect NOM esa uning haqiqiy joyi va qaysi containerga ulanganini ko'rsatadi.

82 Volume backup qanday olinadi?
✓ 🧠 Javob

Volume'ni vaqtincha yordamchi containerga ulab, ichidagini arxivlab tashqariga chiqarish: docker run --rm -v data:/data -v $PWD:/backup alpine tar czf /backup/data.tar.gz /data. DB uchun esa ko'pincha to'g'ri yo'l — DB'ning o'z dump vositasi (pg_dump) bilan izchil nusxa olish.

Docker resources

83 Container CPU limit qanday belgilanadi?
✓ 🧠 Javob

docker run --cpus=1.5 image — container eng ko'p 1.5 yadro quvvatini oladi. --cpu-shares esa faqat nisbiy ulush beradi (raqobat bo'lganda kim ko'proq olishi), qat'iy chegara emas.

84 Container memory limit qanday belgilanadi?
✓ 🧠 Javob

docker run -m 512m image. Limitga urilsa container OOMKilled bo'ladi. --memory-swap bilan swap chegarasi ham beriladi.

85 OOMKilled nega bo'ladi?
✓ 🧠 Javob

Container o'ziga qo'yilgan xotira limitidan oshib ketdi — host'da xotira bo'lsa ham o'ldiriladi. Sabablari: limit juda kichik, dasturda leak, yoki yuk oshganda xotira talabi o'sishi. Belgisi: exit code 137, docker inspectda OOMKilled: true.

86 docker stats nima ko'rsatadi?
✓ 🧠 Javob

Har container uchun jonli ko'rsatkich: CPU foizi, xotira ishlatilishi va limiti, tarmoq I/O, blok (disk) I/O, process soni. "Kim resurs yeyapti?" degan savolga birinchi javob.

87 CPU throttling nima?
✓ 🧠 Javob

Container CPU chegarasiga urilganda yadro uni vaqtincha to'xtatib turadi — o'ldirmaydi, sekinlashtiradi. Belgisi: CPU limitga tiqilib turadi, javob vaqti o'sadi, lekin xato yo'q. Shuning uchun "sekin ishlayapti" muammosida CPU limitini ko'rish kerak.

88 Memory va CPU limit muammolari qanday farq qiladi?
✓ 🧠 Javob

Xotira — qattiq chegara: oshsa container o'ldiriladi (OOMKilled, 137). CPU — yumshoq chegara: oshsa container sekinlashtiriladi (throttling), lekin tirik qoladi. Bir jumla: xotira o'ldiradi, CPU sekinlashtiradi.

89 Nega production'da resource limit kerak?
✓ 🧠 Javob

Bitta container butun mashinani yeb qo'yishining oldini oladi (shovqinli qo'shni muammosi); yuqoridan rejalashtirish imkonini beradi (mashinaga nechta container sig'adi); xotira leak'ini erta ko'rsatadi; va boshqa xizmatlarni himoya qiladi. Limitsiz muhitda bitta nosoz dastur hammani yiqitadi.

90 Host resurslari va container limitlari qanday bog'liq?
✓ 🧠 Javob

Limit — host resursining ulushi, qo'shimcha resurs emas. Limitlar yig'indisi host imkoniyatidan katta bo'lsa (overcommit), yuk oshganda containerlar bir-biri bilan raqobat qiladi. Shuning uchun container OOM (limitga urildi) va host OOM (mashinada xotira tugadi) ikki boshqa hodisa — birinchisi limitni, ikkinchisi butun mashinadagi yukni ko'rishni talab qiladi.

Docker security

91 Nega container root bilan ishlatilmasligi kerak?
✓ 🧠 Javob

Container ichidagi root ko'p hollarda host root'iga yaqin imkoniyat beradi: chiqib ketish (escape) zaifligi topilsa yoki noto'g'ri mount qilingan bo'lsa, zarar butun mashinaga yoyiladi. Shuning uchun Dockerfile'da USER app bilan root bo'lmagan foydalanuvchiga o'tiladi.

92 Privileged container nima?
✓ 🧠 Javob

--privileged bilan ishga tushirilgan container: host qurilmalariga kirish va deyarli hamma imkoniyat (capability) beriladi — izolyatsiya amalda yo'q. Faqat juda zarur hollarda ishlatiladi; odatda kerakli capability'ni --cap-add bilan nuqtali berish to'g'ri.

93 Capabilities nima?
✓ 🧠 Javob

Linux root huquqlarining mayda bo'laklari (masalan NET_ADMIN — tarmoq sozlash, NET_BIND_SERVICE — 1024'dan kichik portga bind qilish). Docker default'da ko'pini olib tashlaydi; kerakligini --cap-add, keraksizini --cap-drop bilan boshqarasiz.

94 Image scanning nima?
✓ 🧠 Javob

Image ichidagi paket va kutubxonalarni ma'lum zaifliklar bazasiga solishtirib tekshirish (Trivy, Grype, registry skaneri). CI'da avtomatlashtiriladi: yangi image build bo'lganda skanerdan o'tadi va jiddiy zaiflik topilsa deploy to'xtatiladi.

95 Nega kichik base image xavfsizroq?
✓ 🧠 Javob

Kamroq paket — kamroq zaiflik va kichik hujum yuzasi. Bundan tashqari buzg'unchiga foydali vositalar (shell, paket menejeri, compiler) bo'lmaydi. Shuning uchun slim, alpine yoki distroless asoslari tanlanadi.

96 Secretlarni Docker'da qanday boshqarish kerak?
✓ 🧠 Javob

Image ichiga yozmaslik — ENV ham, ARG ham image/build tarixida qoladi. To'g'ri yo'llar: runtime'da environment orqali berish, fayl sifatida mount qilish, maxfiy do'kondan olish (Vault, cloud secret manager), BuildKit secret mount. Va .dockerignorega .env, kalitlarni qo'shish.

97 Nega .env faylni image ichiga qo'ymaslik kerak?
✓ 🧠 Javob

Image tarqatiladi — registry'da turadi, boshqalar pull qiladi. Ichidagi parol va kalit hamma uchun ochiq bo'ladi; qatlamlar tarixidan o'chirish ham qiyin (keyingi qatlamda o'chirsangiz ham oldingi qatlamda qoladi). Shuning uchun secret faqat runtime'da beriladi.

10 savol

Docker Compose

98 Docker Compose nima?
✓ 🧠 Javob

Bir nechta containerni bitta YAML faylda tasvirlab, bir buyruq bilan boshqarish vositasi. docker compose up butun stack'ni (frontend, backend, DB, cache) ko'taradi, down tushiradi.

99 Compose'ning asosiy tushunchalari?
✓ 🧠 Javob

services — qaysi containerlar ishga tushadi va qanday sozlama bilan. networks — kim kim bilan gaplashadi. volumes — qaysi ma'lumot saqlanadi.

100 services nima?
✓ 🧠 Javob

Compose'dagi har bir container tavsifi: qaysi image yoki build konteksti, portlar, environment, volume'lar, dependency va restart siyosati.

101 depends_on nima qiladi?
✓ 🧠 Javob

Faqat start tartibini belgilaydi — "postgres avval ko'tarilsin". Lekin bu tayyorlikni kafolatlamaydi: container ishga tushgani DB so'rov qabul qilishga tayyor degani emas. Tayyorlik uchun healthcheck (condition: service_healthy) yoki dasturda retry kerak.

102 Compose'da networking qanday ishlaydi?
✓ 🧠 Javob

Compose loyiha uchun alohida tarmoq yaratadi va hamma service'ni shunga ulaydi. Service'lar bir-birini nomi orqali topadi: backend postgres:5432 deb ulanadi. Tashqariga faqat ports: bilan e'lon qilingan portlar chiqadi.

103 Compose'da volumes qanday ishlatiladi?
✓ 🧠 Javob

Yuqori darajadagi volumes: bo'limida nomli volume e'lon qilinadi, service ichida volumes: - data:/var/lib/postgresql/data deb ulanadi. Bind mount ham shu joyda host yo'li bilan yoziladi (./src:/app).

104 Compose va production farqi?
✓ 🧠 Javob

Compose bitta mashinada ishlaydi: avtomatik masshtablash, o'zini davolash, rolling update va node'lar orasida rejalashtirish yo'q. Production'da bu vazifalarni orkestrator (Kubernetes) bajaradi. Compose — development, lokal test va oddiy bitta-server deploy uchun juda qulay.

105 Nega Compose local development uchun qulay?
✓ 🧠 Javob

Butun stack bitta faylda tasvirlanadi va up bilan ko'tariladi — yangi dasturchi bir buyruq bilan ishga tushadi. Kod bind mount orqali darhol ko'rinadi, loglar bir joyda, down hammasini tozalaydi.

106 docker compose up va docker compose up -d farqi?
✓ 🧠 Javob

up — loglarni terminalga chiqarib oldinda ishlaydi (Ctrl+C to'xtatadi). up -d — fon rejimida ishga tushiradi, terminal bo'shaydi; loglarni docker compose logs -f bilan ko'rasiz.

107 docker compose down nima qiladi?
✓ 🧠 Javob

Compose yaratgan containerlarni to'xtatib o'chiradi va tarmoqni olib tashlaydi. Nomli volume'lar saqlanadi — ma'lumot qoladi. Ularni ham o'chirish uchun down -v kerak (ehtiyot bo'lish shart).

10 savol

Docker debugging

108 Container darhol exit bo'lsa nima tekshirasiz?
✓ 🧠 Javob

Uch qadam: docker ps -a — exit code qancha; docker logs — oxirgi nima deb chiqdi; docker inspect — sozlama, CMD/ENTRYPOINT, OOMKilled flagi. Sabab deyarli har doim: CMD ishini tugatdi yoki xato bilan yiqildi.

109 docker logs nima ko'rsatadi?
✓ 🧠 Javob

Container'ning asosiy process'i stdout/stderr'ga yozgan hamma narsani. -f jonli kuzatadi, --tail 50 oxirgi qatorlarni, --since 10m vaqt bo'yicha filtrlaydi. Muhim: dastur faylga yozsa bu yerda ko'rinmaydi — log stdout'ga chiqarilishi kerak.

110 docker inspect nima ko'rsatadi?
✓ 🧠 Javob

Container yoki image'ning to'liq tavsifi JSON'da: sozlama (CMD, ENTRYPOINT, ENV), tarmoq va IP, mount'lar, holat va exit code, OOMKilled flagi, restart siyosati.

111 docker exec bilan containerga qanday kirasiz?
✓ 🧠 Javob

docker exec -it sh (yoki bash) — ishlayotgan container ichida qobiq ochadi. Shundan keyin xuddi oddiy serverdagidek tekshirasiz: fayllar, ss -lntup, env, curl. Container ishlayotgan bo'lishi kerak.

112 Container running, lekin app javob bermayapti — qadamlar?
✓ 🧠 Javob

Tartib bilan: 1) logs, 2) process tirikmi (docker top), 3) port eshityaptimi (ss -lntup), 4) bind address to'g'rimi (0.0.0.0 va 127.0.0.1), 5) tarmoq/DNS, 6) environment va config, 7) dependency javob beryaptimi.

113 Container ichida process ishlayotganini qanday tekshirasiz?
✓ 🧠 Javob

docker top — host tomondan container process'larini ko'rsatadi. Yoki ichkariga kirib ps aux. Muhim tekshiruv: PID 1 kim — dasturmi yoki shell (shell bo'lsa signal muammosi bo'ladi).

114 Port ochiq, lekin ulanmayapti — nima tekshirasiz?
✓ 🧠 Javob

Zanjirni oxiridan boshlaysiz: dastur qaysi manzilga bind qilgan (127.0.0.1 bo'lsa sabab topildi); port mapping to'g'rimi (docker ps PORTS ustuni); container ichidan ishlayaptimi (docker exec ... curl localhost:PORT); host firewall to'smayaptimi.

115 docker system df nima ko'rsatadi?
✓ 🧠 Javob

Docker qancha disk yeganini: image'lar, containerlar, volume'lar va build cache bo'yicha, shu jumladan qaytarib olinadigan hajm. "Disk to'ldi" muammosida birinchi qaraladigan joy.

116 docker system prune nima qiladi?
✓ 🧠 Javob

Ishlatilmayotgan obyektlarni o'chiradi: to'xtagan containerlar, egasiz image'lar, ishlatilmayotgan tarmoqlar va build cache. -a qo'shilsa hamma ishlatilmayotgan image ham ketadi, --volumes qo'shilsa volume'lar ham — bu ma'lumotni o'chiradi.

117 Disk to'lib qolsa Docker'da nima tekshirasiz?
✓ 🧠 Javob

docker system df bilan taqsimotni ko'rasiz. Ko'p uchraydigan sabablar: yig'ilib qolgan eski image va build cache; cheklanmagan container loglari (rotation sozlanmagan); egasiz volume'lar. Yechim: prune, log driver limitlari (max-size, max-file) va kerakli volume'larni ajratib olish.

7 savol

Docker production

118 Nega container "virtual server" emas?
✓ 🧠 Javob

Chunki uning hayoti asosiy process hayotiga bog'liq: PID 1 tugasa container ham tugaydi. Serverdek "yoqib qo'ysam turadi" degan xatti-harakat yo'q. Shuningdek ichidagi yozuv qatlami vaqtinchalik — holat volume'da bo'lishi kerak.

119 Bitta container ichida bir nechta service ishlatish nega yomon?
✓ 🧠 Javob

Container bitta vazifa uchun mo'ljallangan: PID 1 bitta bo'ladi, shu sababli signal, restart, sog'lomlik va log bitta process bilan bog'lanadi. Ichida ikkita xizmat bo'lsa — biri o'lsa container tirik ko'rinadi, log aralashadi, alohida masshtablash mumkin emas. To'g'ri yo'l: har xizmat — alohida container.

120 Immutable infrastructure nima?
✓ 🧠 Javob

Ishlayotgan muhitni joyida o'zgartirmaslik tamoyili: o'zgarish kerak bo'lsa yangi image build qilinadi va eski nusxa yangisi bilan almashtiriladi. Natijada har muhit bir xil bo'ladi, orqaga qaytish oson va "bu serverda nima qilingan edi?" degan savol yo'qoladi.

121 Nega container tez start bo'lishi kerak?
✓ 🧠 Javob

Orkestrator containerni tez-tez qayta yaratadi: deploy, masshtablash, node almashtirish, nosozlikdan tiklanish. Start sekin bo'lsa — rolling update uzoq davom etadi, avtomatik masshtablash yukka yetib olmaydi va tiklanish vaqti o'sadi.

122 Logging Docker'da qanday tashkil qilinadi?
✓ 🧠 Javob

Dastur logni faylga emas, stdout/stderr'ga yozadi; Docker uni log driver orqali yig'adi (json-file, journald, yoki tashqi tizimga). Fayl driverida rotation (max-size, max-file) albatta sozlanadi. Markazlashtirilgan yig'ish bilan loglar bir joyda qidiriladi.

123 Healthcheck nima?
✓ 🧠 Javob

Container sog'lomligini o'lchaydigan buyruq (HEALTHCHECK yoki Compose'dagi healthcheck:): davriy bajariladi va natijaga qarab holat healthy/unhealthy bo'ladi. Foydasi: "ishlayapti" bilan "javob beryapti" farqlanadi.

124 Restart policy production'da qanday tanlanadi?
✓ 🧠 Javob

Uzoq ishlaydigan xizmat uchun unless-stopped yoki always — nosozlikdan o'zi tiklanadi, lekin qo'lda to'xtatilgan bo'lsa turmaydi. Bir martalik ish uchun no yoki on-failure chegara bilan. Ogohlik: restart policy sababni yashiradi — restart loop bo'lsa log va exit code'ni ko'rish shart.
